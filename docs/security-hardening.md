## Implemented, in priority order

1. **Browser execution and framing protections.** Fresh request nonces, enforced CSP, no inline event handlers, blocked object embedding, restricted forms/base URLs, anti-framing, nosniff, no-referrer and limited browser permissions. Nonces reach Next and next-themes. CMS homepage preview alone permits same-origin framing. Auth, admin and portal pages cannot opt into that exception. Nonce HTML is private/no-store. Production HTTPS configuration enables HSTS without automatically claiming subdomains. Stripe scripts/frames are allowed for navigation into checkout; no analytics were added.
2. **Proxy trust configuration and login lockout accounting.** Validated `CUSTOMER_IP_HEADER` and `CUSTOMER_TRUSTED_PROXIES`; invalid headers, malformed CIDRs and catch-all `/0` trust are rejected. Only an actual `401 INVALID_EMAIL_OR_PASSWORD` increments account password failures, not throttling or provider errors. **Production remains dependent on trusted ingress configuration below.**
3. **Unsafe financial text.** Reject XML-illegal code points, lone surrogates, bidi overrides and invisible controls in company/catalog inputs and before invoice approval/export. Uncertain extraction remains editable. Both XML generators refuse unsafe data; financial values are never silently rewritten. Legitimate international names, combining marks, ZWNJ/ZWJ and supplementary Unicode remain supported. Filenames remove controls/separators and cannot be truncated through a surrogate pair.
4. **Authentication request and recovery protections.** Every POST body to customer auth is stream-bounded to 64 KiB. Password changes enforce old-session revocation even if a direct caller explicitly submits `revokeOtherSessions:false`. New password-reset identifiers are hashed through Better Auth's supported storage option. Reset consumption is single-use under concurrent requests, revokes sessions and retains MFA. Existing short-lived reset links remain compatible with Better Auth's migration fallback; MFA identifiers retain their existing format for revocation queries.
5. **Recipient mail quotas.** Verification and reset messages each have a separate atomic budget of 5/hour and 10/24 hours per normalized recipient. Counters store a keyed hash, not the mailbox. SMTP attempts reserve capacity first; suppressed delivery has the same outward result. MFA security notifications and invitations do not share this budget. Counters expire and stale entries are removed after seven days. Apply customer migration `0026_customer_email_limits.sql` before deploying application code.
6. **Hybrid-invoice review.** Incoming ZUGFeRD keeps authoritative XML and the supplier original unchanged. Local PDF text is compared with XML invoice number, gross total, bank account and buyer/supplier VAT IDs. Missing values generate localized review warnings, including an explicit warning for absent text. This is a presence heuristic, **not proof that visible pixels agree**: hidden text, scanned pages, unusual amount formatting and duplicate values still require human review. No external OCR was added. Technical validator success never certifies authenticity. The server requires `originalChecked:true` before marking incoming invoices reviewed and records the confirmation against the source hash. The confirmation explicitly covers financial details and independently checking unexpected bank changes.
7. **Exact admin prices.** Billing price inputs use strict decimal syntax and integer cents, rejecting exponent notation, trailing garbage, ambiguous separators and excess precision/range. Provider prices remain selected by the server.
8. **Supply-chain delay.** `minimumReleaseAge: 4320` adds a three-day delay while preserving the existing install-script allowlist, dependency lockfile and theme patch. Security updates pin Next/eslint-config-next 16.3.6, Sharp 0.35.4 and Vitest 4.1.11, with reviewed transitive overrides. Payload packages remain aligned at 3.89.0. See the dependency notes below. Use a supported pnpm version (the verification environment used 11.19.0; pnpm 12 is outside the declared engine range).
9. **File detection.** Reject XML-shaped HTML at the lightweight root check before upload acceptance. Full XML parsing still happens after malware scanning.

10. **Identity disclosure and uniqueness.** Generic duplicate signup responses derive the same display name as new accounts. Case-insensitive email uniqueness is enforced in PostgreSQL; migration `0027_customer_email_uniqueness.sql` fails safely if legacy conflicts need review.

## Required deployment inputs

### Ingress and trusted client IP

Set the canonical HTTPS `BETTER_AUTH_URL`, then identify the actual ingress and its header contract. `CUSTOMER_IP_HEADER` defaults to `x-forwarded-for`; `CUSTOMER_TRUSTED_PROXIES` is a comma-separated list of exact IPs/CIDRs of trusted proxy hops. Do not copy example networks into production or trust arbitrary private ranges.

Better Auth interprets the forwarded chain; these settings do not authenticate the direct sender. The origin must be reachable only through the trusted ingress, and the ingress must overwrite the client-IP header or implement a documented, correctly trusted chain. Test direct-origin denial, a client-supplied header, multiple hops, IPv4/IPv6, and separate clients' rate buckets. With no trustworthy IP, Better Auth falls back to a shared bucket. The production platform is still unknown, so no deployment trust values were invented.
